Alumni Posts from eligible verified alumni affiliations and accessible alumni groups Professional insight, mentorship, opportunities and alumni discussions. Alumni with multiple affiliations should be discoverable through each valid affiliation; offer an institution filter rather than silently mixing all institutional posts. 6.2 Interest / keyword map The keyword map should become a topic map, not a raw frequency counter. Normalize synonyms and related terms (for example, ΓÇ£PostgresΓÇ¥ and ΓÇ£PostgreSQLΓÇ¥) into canonical topics and optionally parent topics. Do not mine private one-to-one chats by default; use disclosed, permitted signals such as follows, saves, searches and feed interactions. 6.3 Ranking pipeline Candidate generation: retrieve a limited candidate set from recent posts, followed accounts/topics, institution/group indexes, topic matches and a small public discovery pool. Eligibility filtering: remove inaccessible, deleted, blocked, muted or moderated content before it reaches the ranker. Baseline ranker: deterministic scoring using topic relevance, behavioural intent, graph affinity, freshness, content quality, relevant verification and normalized popularity. Optional FlashRank reranking: run only on already eligible candidates, behind a RankingService interface with timeout and fallback. Post-reranking: apply freshness, near-duplicate suppression, author/topic diversity and a discovery budget. Final permission check: revalidate eligibility before returning results, especially if membership/block state can change during processing. Feedback: record impressions and meaningful interactions so the system can be evaluated and improved. 6.4 Initial score and fallback Use a configurable weighted baseline rather than claiming an unvalidated model is optimal. Example starting score: 0.28 topic relevance + 0.20 behavioural relevance + 0.15 graph affinity + 0.12 freshness + 0.10 content quality + 0.10 relevant verification + 0.05 normalized popularity. Normalize feature values to a common scale. These are provisional hackathon weights and must be evaluated against a chronological baseline. FlashRank is a replaceable reranking adapter, not an authorization system and not a requirement for the baseline to function. If the adapter is unavailable, slow or errors, return the eligible candidates in deterministic baseline order. Do not let a ranking score override access rules. 6.5 Candidate-set limits For an MVP, retrieve a modest, bounded candidate set (for example, 100ΓÇô300 eligible candidates depending on database performance), rerank only that set, and paginate the final list with a stable cursor. This is a starting point to benchmarkΓÇönot a guaranteed performance target. Avoid loading the entire post collection into application memory. 6.6 Feed experience and interaction contract The three primary feed tabsΓÇöFor You, Alumni and StudentsΓÇömust be clearly distinct, with Following available as a user-directed stream. On small screens, the same destinations may use a compact tab row or equivalent accessible navigation; do not bury the feeds inside a multi-step menu. For You is the default discovery surface, but the user can switch to Following or a chronological/latest mode without losing context. A post card should show author identity, relevant affiliation and verification labels, timestamp, audience context, post content, and only the actions valid for that viewer. Expose ΓÇ£Why am I seeing this?ΓÇ¥ with a short reason such as ΓÇ£Matches your interest in distributed systemsΓÇ¥ or ΓÇ£Posted by an alumnus from your institution.ΓÇ¥ Do not reveal private inferred scores or sensitive activity histories. Provide practical feedback actions: Save, Not interested, Mute topic, Mute author, Report and Undo where applicable. Confirm destructive or high-impact actions and give a way to reverse accidental hides. Use a ΓÇ£New postsΓÇ¥ affordance or explicit refresh rather than silently shifting items while the user is reading. Keep scroll position stable when returning from a profile. Use cursor pagination and a consistent page boundary. Do not fetch the entire feed upfront or produce duplicate cards across pages. Cold-start users receive a useful mix of recent eligible institutional content, optional declared topics and a small amount of public discovery. Never show a blank screen merely because the user has little history. If reranking is unavailable, visibly keep the feed functional; do not show a technical stack trace or block the user from browsing. 7. Professional Discovery and Search Search is a separate intent-driven system. Feed ranking asks what might be useful next; search should prioritize the explicit query and structured constraints. Search should return people, posts, groups, institutions and organisations as separate result types, with people discovery as the core MVP workflow. 7.1 People search Exact structured filters: institution, programme, department, batch, company, role/job title, skills and mentorship/referral availability. Text retrieval: name, bio, skills, company and role fields with sensible normalization and aliases. Optional semantic retrieval: related concepts that do not share exact keywords; defer if it risks the end-to-end workflow. Graph features: direct connection, shared group, shared institution and second-degree relationship as tie-breakersΓÇönot as hard requirements. Explainable result cards: institution affiliation status, employment verification status, matching skills, current availability and connection distance where safe. Visibility and block filtering must apply to profiles and result snippets before returning them. 7.2 Example search ranking An initial profile-search score may combine query/text relevance (35%), structured-field match (25%), relevant verification and freshness (15%), graph proximity (10%), profile completeness (10%) and normalized popularity (5%). These weights are provisional and should vary by query type. For a company-specific query, an exact current company match should outrank generic popularity. 7.3 Student-to-alumnus workflow 1. Student searches for an alumnus at a target company, optionally specifying role or skill. 2. System returns eligible profiles and labels institution verification separately from employment status. 3. Student opens a profile and sees the alumnus's stated availability for mentorship, referrals or general questions. 4. Student sends a purpose-specific connection request with a short message. 5. Alumnus accepts or declines; accepted status unlocks private messaging. 6. Measure whether the connection leads to a useful conversation or introduction. 7.4 Search experience and result explanations The main search entry should accept natural phrasing, names, skills, companies and roles. Debounce typing and keep the current query visible while filters are applied. Present company, role, skill, institution, programme, department, batch and availability as removable filter chips. Make Clear all visible when filters are active. Profile result cards should show only decision-useful information: name, verified affiliation, employment verification state, relevant skills, company/role, institution context and stated availability. Distinguish ΓÇ£employer-verifiedΓÇ¥ from ΓÇ£self-reportedΓÇ¥ and ΓÇ£verification pending.ΓÇ¥ Never use a generic green tick that could imply all claims on the profile are verified. For empty results, suggest spelling alternatives, broader role/skill terms, removing a filter or exploring adjacent institutions only where policy allows it. Search must not reveal hidden group names, private profile fields or content snippets the requester cannot access. Do not leak the existence of a private object through autocomplete or result counts. 8.
